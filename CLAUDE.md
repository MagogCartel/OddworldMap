# CLAUDE.md

Guidance for AI agents working in this repo. User-facing docs (controls, rebuild instructions, format overview) live in [README.md](README.md) — read that first; this file covers what is not obvious from the code and the traps that cost hours to find.

## Source vs generated

- Source: the viewer — `index.html`, `css/main.css` and the ES modules under `js/` (dependency-free vanilla JS, no build step; `js/main.js` is the boot entry, `js/state.js` holds shared state + world→draw transforms, and selection announces itself via a `selection-changed` window event so modules stay one-directional) — plus `annotations.json` (hand-curated names/notes the discs don't provide; a curated name deliberately overrides the in-game one but must contain it — refine, don't erase, test-enforced. A path carries at most one of the two labels the games define, and only a `name` is one: it is what the game calls the place (AO R2's zulags, from the save slots), so an override answers to it. A `section` is which half of a level the path belongs to — the AE ender display name, stamped on paths nothing else names — so it sits beside the curated name rather than inside it, and the viewer shows it on the place panel and the path button's tooltip. A path entry is a bare name string or `{name?, note?}`, so only the paths with something extra to say expand; either half stands alone. A note-only entry is legal for a path but not for a level: a path is on the map and identified by its id whatever it is called, while a level entry exists to name a level the map never renders, so a note there would have nothing to hang on. Requiring a name would otherwise force one to be invented — most paths have no in-game name, which is why the file exists. `sanitizeAnnotations` collapses the union, so callers only ever see the object. A note is written as ordinary prose, capitalized and punctuated — it is a sentence about the place, not a UI label, and it reaches the reader through the place panel) and `tools/build_map.py`, `tools/cam2rgba.cpp` and the vendored `PSXMDECDecoder.*` / `Types.hpp`.
- `glossary.json`: **hand-curated** (like `annotations.json`, not generated) plain-English field meanings, one game-agnostic file. Three resolution tiers, most-specific first: `byType` (`"ObjectType.field"`), `byGameType` (a field's decomp game type, e.g. `Path_Slig::StartState` — the group of object types sharing that field's meaning, the same key `enum_labels` uses), `byField` (a global by name). Loaded at boot (`setGlossary` in [js/glossary.js](js/glossary.js)); [js/fields.js](js/fields.js)'s `fieldHelp(game, type, field)` composes the prose with the field's full value list (from `TRANSFORM`/`enum_labels`) for the picker and screen-list definitions, handed over as a `data-tip` attribute on the field name ([js/anchortip.js](js/anchortip.js)). A field with no entry has no def (graceful); a test cross-checks every key against the shipped data so a typo can't ship. Adding a definition is one JSON line — the fields objects show by default are nearly all covered, the picker-only long tail is not (those meanings need game knowledge).
- Generated **and committed** (they are the site's data): `map_data_ao.json`, `map_data_ae.json`, `cams/ao/**`, `cams/ae/**`. Regenerate with the builder from disc images; never hand-edit.
- `field_types_{ao,ae}.json`: generated **and committed** viewer sidecar mapping each object type to its enum-typed fields' game types (`{"Slig": {"start_state": "Path_Slig::StartState", …}}`). Derived from the decomp alone (no disc) via `build_map.py --emit-field-data`, and re-emitted on every normal build so it stays in sync. The viewer loads it at boot (`setFieldTypes` in [js/fields.js](js/fields.js)) and keys value transforms by a field's game type — a value's text written once per type and shared across every object that carries it (Slig/SligSpawner/SligGetPants all share `Path_Slig::StartState`) while an unrelated same-named field stays separate (a Door's `start_state` is `DoorStates`, its own key). Only enum/Choice/Scale fields appear; bare-int fields carry no type. A small `_FIELD_TYPE_OVERRIDES` table corrects decomp quirks at emission — the schema cache stays faithful to the source (AE declares SligSpawner's `chase_abe_when_spotted` as a direction; it behaves as a boolean). Correct such quirks here in the builder, never by patching the local `alive_reversing` checkout — a patch would make the emit unreproducible from a clean tree; fixing it upstream and re-pinning is the path to retiring an override.
- `enum_labels_{ao,ae}.json`: generated **and committed** viewer sidecar mapping each enum game type to its `{value: text}` labels (`{"DoorStates": {"0": "open", "1": "closed", …}}`), so enum fields render as words without the viewer hand-maintaining them. Generated by `parse_enum_labels` (`--emit-field-data`, no disc) from the decomp's enum definitions (authoritative values, explicit `= N` or positional) and its `AddEnum` blocks (curated labels, else a label derived from the enumerator name); labels are lowercased to the viewer's style, keyed to line up with `field_types`, and limited to the types some field is actually declared as (the decomp defines many enums that aren't fields). Per game — the same type's values can differ (Slig `start_state` 5 is `falling to chase` in AO, `unused` in AE). The basic value-types (`Choice`/`Scale`) are **excluded**: the viewer owns those semantic transforms (bool, full/half) in `js/fields.js`'s `TRANSFORM`, and a hand transform there wins over a generated label; direction enums are generated like any other (left/right). Definitions are swept from the game's whole AliveLib tree plus AliveLibCommon (the include graph can't reach them all — `SwitchOp` is only ever forward-declared where fields use it), with the sibling game's tree as a fill-only fallback for shared types (AO fields use AE's `XDirection_short`). Comments are stripped before parsing — the word "enum" inside one otherwise swallows the definition that follows it, and a comma inside one once minted a phantom enumerator. A bare enum name defined differently in two headers, or an initializer the parser can't value, makes the type unlabelable, and the emit fails loudly if any field actually uses such a type — labels must never ship silently wrong.
- `tools/data/pathdata_ao.json` / `pathdata_ae.json`: cached level/path tables and TLV type enums parsed from the alive_reversing decompilation. Used as-is by builds; only re-parsed when the cache file is deleted, which requires an `alive_reversing` checkout as a sibling directory of this repo (AO tables come from commit `c1ba4c6c8`, AE tables from the current sources).
- `tools/data/objects_ao.json` / `objects_ae.json`: cached per-type field layout (`[payload word, snake_case name]` per field, plus a third element — the field's game type — where the decomp declares an enum/Choice/Scale rather than a bare int), parsed from the relive_api CTOR blocks (`Source/Tools/relive_api/Tlvs{AO,AE}.hpp`) by `parse_object_schema`. Same cache discipline as pathdata (re-parsed only when deleted). Drives the generic `object_fields` extractor, which emits every field of a gameplay object (`GAMEPLAY_FIELD_TYPES` in `build_map.py`) raw into `t.fields` — it reads only word+name, so the type is metadata and `map_data` is byte-identical whether or not types are present. Values are read as s16 and stored raw — which fields to show and how their values render are the viewer's job ([js/fields.js](js/fields.js), driven by the `field_types` + `enum_labels` sidecars), so the disc is never needed again to surface or relabel a field. Parser gotcha: the payload word comes from the `field_XX` hex offset in the member name, but the name lies two ways. The decomp sometimes numbers *sequential* members with one offset (Door's 8 hub ids are all `field_22_hubN`); and a member of an intermediate base struct numbers from that struct's own start, so it computes *below* the payload base (`Path_WellBase`'s `field_0_scale`..`field_6_anim_id`, and ContinueZone's sole `field_10_zone_number` — Path_TLV is 0x18 wide, so the name's 0x10 lands in the rect). Both fail to increase the offset, so the one positional rule — take the next word — answers both; a below-base name must not be skipped, or the fields vanish silently with no `raw=` to show for it. `_SCHEMA_LAYOUT_OVERRIDES` is left for what the CTOR genuinely can't express: an empty layout marking a field-less type (AO RingCancel) so it still retires its raw fallback. Because `object_fields` returns a dict for any schema'd type (empty for the field-less ones), a `GAMEPLAY_FIELD_TYPES` object never falls back to a `raw=` dump. A base struct's members reach the *layout* this way but not their *type* — `parse_member_types` reads a struct's own body only, so the wells' `scale` arrives untyped and renders raw. The field type comes from `parse_member_types`, which parses the data-struct member declarations across `Tlvs{AO,AE}.hpp` and every `AliveLib*` header it includes; enum leaf names repeat across the decomp (`StartState` is both a Slig enum and a MeatSaw enum), so a nested enum is qualified with its owning struct (`Path_Slig::StartState`) and the decomp's own qualified references carry the cross-object sharing. Field names collide across types (`start_state` is a Slig AI state and a Door lock state), so `js/fields.js` keys value transforms by this game type (grouping objects that share an enum, keeping unrelated same-named fields apart) and still scopes default-visibility by `Type.field`.

## Build & verify

- `npm run lint` — ESLint over the viewer modules; CI runs it on every push. There is no JS build step: the modules are served as-is, so lint is the only pre-runtime error check.
- `python3 -m compileall -q tools/` and `ruff check tools/` — the builder's static checks; CI runs both on 3.12. `ruff.toml` selects the defect rules alone (undefined names, unused imports, f-string and syntax errors), not ruff's default set, which fights the parsers' deliberate compactness. The supported floor is 3.8, which CI cannot exercise (EOL, absent from current runner images), so 3.9+ syntax would only surface locally.
- `python3 -m unittest discover -s tools/tests` — stdlib-only tests for the builder's pure functions (chunk walking, the LZ variant, `object_fields`' payload clamp, the label/comment/brace helpers), plus reproducibility tests that re-emit the committed `field_types_*`/`enum_labels_*` sidecars into a temp dir and compare bytes. No disc image is needed; the enum-label pair skips without an `alive_reversing` checkout, so CI covers everything except those two. A parser reached only through a nested helper (AE's `positional_rows`, the enum body loop) can't be tested until it's hoisted.
- `npm test` — `node --test` unit tests under `tests/unit/` for the DOM-free modules (`annotations`, `config`, `state`, `util`, `model`, `settings`): geometry transforms, TLV destinations, entry paths, permalink format, settings sanitizing, plus schema checks over the shipped data files. Those modules must stay importable in bare Node — no `window`/`document` at module top level (imports.test.js enforces this; `settings` additionally keeps its localStorage access inside guarded calls).
- `python3 tools/build_map.py --game AO|AE --disc <image.bin ...>` — AE takes both discs; env fallbacks are `$ODDWORLD_DISC_AO` / `$ODDWORLD_DISC_AE` (2352-byte-sector raw images). `cam2rgba` is compiled automatically on first run; `oxipng` must be installed (every emitted PNG is losslessly recompressed with `-o 2 --strip safe`, so byte-determinism of images also depends on the oxipng version — committed images were made with oxipng 10.x).
- The pipeline is byte-deterministic. To verify builder changes, build into a scratch dir with `--out` and `cmp` the data file (and spot-check PNGs) against the committed outputs.
- `--levels X,Y` subset builds merge into the existing data file — they do not clobber other levels.
- Existing cam PNGs are skipped for speed, so a level whose decode previously half-completed keeps stale outputs; delete `cams/<game>/<LEVEL>/` for a clean rebuild of that level.
- `sw.js` (root, a classic script — not an ES module; linted with `serviceworker` globals, no unit tests by design) caches `cams/**/*.png` cache-first in the Cache API, because GitHub Pages re-stamps HTTP validators on every deploy. It is opt-in: the worker can't read settings, so `settings.js` gates it on the `cacheImages` setting (off by default) — enable registers the worker and creates the `cams-on` marker bucket the worker checks before storing; disable deletes every `cams-*` bucket and unregisters. The marker, not unregistration, is what stops caching immediately: an already-controlling worker keeps handling fetches until reload, and module state wouldn't survive an idle-worker restart. Bump its `CACHE_NAME` whenever cam artwork is regenerated, or opted-in visitors keep the old art forever. After rebuilding cams locally, use DevTools → Application → "Bypass for network" (or Clear site data) to see the new images.
- `initSettings`'s `bind` is the funnel for the boolean settings: seeding the checkbox, persisting, marking a row whose value isn't its default, and the apply callback all hang off one call, so a new boolean setting gets the lot by being bound. The show-more checkbox flips `fieldPrefs.mode` rather than a boolean, so it is wired by hand and is the one control that has to be updated alongside `bind`.
- **The stylesheet's shared vocabulary** ([css/main.css](css/main.css)) is what a new surface reaches for instead of restating a treatment. Form controls are the first entry: browsers hand `button`/`input`/`select`/`textarea` a font of their own, so a reset beside the `*` rule gives them the page's, and no rule below it names a font family. That is a category rule rather than a list of today's controls — the drift it retired happened by omission, one rule at a time, and only some of them ever said `font: inherit`. Note the shorthand is the wrong instrument here and was measured as such: it also resets size, weight and line-height, which would take the level and path buttons from 12px to 13px and the close glyph's box from 18x24 to 12x19. `font-family` alone costs one pixel of height on the 11px controls (the search scope buttons and the search results' "show more" rows), where the page font's normal line-height is a pixel taller than the UA font's. A value becomes a `:root` token when components that are otherwise unalike have to agree on it: `--over-rgb` is the one near-black everything floating over the map is tinted from (five alphas across eleven uses), `--surface-float` the opaque tier of it the two tooltips, the screen list and the place panel share, `--shadow-float` and `--shadow-modal` the two elevations. Radii and paddings are deliberately left alone — a size scale over 5/6/8px would buy indirection rather than agreement, since nothing breaks when two components pick different ones. The stacking tiers are tokens for the same reason and sit in `:root` low to high, so their order states a system that nothing else in the repo did: `--z-tip`, `--z-map-overlay`, `--z-scrim`, `--z-drawer`, `--z-map-chrome` (which has to beat the drawer it opens over), `--z-anchor-tip`, `--z-modal`. Naming them shows up the one that reads wrong: `--z-tip` sits *below* the map overlays, backwards for a transient hover affordance, and inert today only because every overlay that captures the pointer hides the tooltip through `#cv`'s `pointerleave` before it could be covered. A treatment that recurs whole becomes a class instead: a dialog is `.overlay` wrapping `.dialog`, holding `.dlg-head` / `.dlg-body` / `.closebtn` (which the screen list's close shares, at its own size), and its module toggles `.open` on the overlay. The state is on the element rather than on `body` precisely so the stylesheet never names a dialog — a fifth one costs no CSS at all unless its width differs from the `--dialog-w` a `.dialog` starts with. `.linkbtn` is the other one: the no-chrome underlined text button, shared by the heading tools, the Fields picker's pair, the sidebar footer and the route bar's undo/clear. It declares no font, deliberately — size is per-surface (11px in the footer, 12px in the route bar, the heading's own for a heading tool), and a `font:` shorthand on the class would break two members in opposite directions, since `.h2tools`'s pair inherits its `h2`'s bold and uppercase while the route bar's keeps the UA `line-height: normal`. Its hover is `:not(:disabled)`, which is what the route bar needs and no other member ever exercises. `.rowbtn` is the full-width row that behaves as a button, with its hover and `.active` states, shared by the screen list and the search results; `.listhead` is the small uppercase divider above a run of them. Both are added alongside the component's own class (`rowbtn cp-row`, `listhead shead`), so what is shared and what is local stay legible in the markup. `.checkrow` is a checkbox and its wording on one line, across the object filters, the Display toggles, the Settings dialog and the Fields picker; padding stays per-surface, which is what keeps the narrow query's fatter touch targets on the two sidebar surfaces and off the dialog's rows.
- `#cv`'s `touch-action` is conditional on purpose: `none` normally, `pinch-zoom` while `body.page-zoomed` is set (`js/interaction.js` watches `visualViewport.scale`, and skips both its own pinch and a touch pointer's `setPointerCapture` in that state — capture would keep the gesture from reaching the browser, while a mouse keeps its capture or a drag released off the canvas never ends). A page zoom can only be undone on a surface that accepts the gesture, and every other one here is dismissible — the drawer closes itself on a path pick, a toast expires on a timer — so the map has to lend its pinch out or a zoomed-in phone is stranded at that scale forever. `body`'s `touch-action: manipulation` is the other half: it drops double-tap zoom, and with it the tap delay a zoomable page otherwise costs, while leaving pinch alone. iOS still enlarges the page when a focused field computes under 16px; that is accepted rather than fought (a 16px search box looked wrong), because the way back out now exists.
- `#placePanel` ([js/place.js](js/place.js)) is a live region, so it announces only what is written into it while it is visible — every fill follows the unhide, and a re-selection of the path it already describes skips the write, because the pushed hash rewrite re-fires `selection-changed` on the same path constantly. Chip and panel are hidden outright under an open drawer on narrow, since the drawer names the place in its own buttons — which means an open panel can be covered rather than closed, and picking a path from that drawer (the only way to pick one there) would otherwise write into a region nobody can read, so `syncPlace` holds the fill until the drawer lifts. It is deliberately not `.chrome`: an embed, where the sidebar starts closed, is where "which level and path is this" is hardest to answer otherwise. It steps down a row while `#routeBar` is up — that bar is wider than the middle of a phone screen, so capping the chip's width can't clear it. Check chip geometry on the longest label either game has, AE BA P4 (`[Demo] Block 3 Slig Bunks: Crawling Sligs`) at 390px and narrower: a representative path is short enough to hide a width regression, and the chip sits above the corner buttons in paint order, so an overlap makes them unclickable rather than merely untidy.
- `#anchorTip` ([js/anchortip.js](js/anchortip.js)) explains any element carrying a `data-tip` attribute. The attribute is the entire interface — there is no registration call and none is wanted; a class like `.gloss` is only the visual cue, so a new consumer writes an attribute and no JS. Because an attribute carries a string and nothing else, the line break is the content model: the first line is the summary, the rest a dimmer `.detail` block. It is a `<body>` child and `position: fixed` because the surfaces that host one scroll (`#sidebar`, `#camPanelBody`) and would clip a tooltip parented inside them; that is the whole difference from `#tip`, which is absolute inside `#main`, follows the cursor and clamps against the canvas — two mechanisms, deliberately not merged, though they share one surface rule and differ only in where each is placed. Its tier (`--z-anchor-tip`) has to beat the narrow drawer it opens inside and the map chrome it crosses on the way out, and stay under the modals, which take the screen; `pointer-events: none` is what stops covering a chrome button from costing a click. The gesture is hover on a mouse and a tap on touch, and the tap is deliberately not consumed — whatever the anchor sits inside still gets its click, so one tap both explains a field and ticks it — meaning nothing here calls `preventDefault`. `pointerover`/`pointerout` are filtered to `pointerType === "mouse"`: a touch fires both around its own tap, so an unfiltered pair would show the tooltip and hide it again inside one gesture. Leaving is asked of the anchor (`anchor.contains(relatedTarget)`) rather than re-resolved from the attribute, so an anchor with element children doesn't flicker as the pointer crosses between them. Check the placement against the bottom edge, where it flips above the anchor, and at 320px, where the width clamp engages.
- `#about` ([js/about.js](js/about.js)) is the fourth dialog on the `.overlay`/`.dialog` + `trapDialogKeys` pattern, and the first to hold links, which is why the trap's tab set counts `a[href]` — the other three hold only controls, so widening it changed nothing for them. Its prose is static markup rather than built by the module, because a legal notice belongs in the page source with scripting off and for anything crawling the site. It is deliberately not `.chrome`: an embed, inside someone else's page, is where a reader can least tell whose map this is, so the unofficial-fan-project notice has to survive one — and the sidebar it opens from is present in an embed, only closed. It states no licence, and that is a decision rather than an omission: the repo holds code written here, one vendored file under another author's copyright, and artwork this project cannot license at all, so a single line of terms in the app would claim all three, and the source link reaches the repository where the licence file is. What keeps two dialogs from ever being open together is not a stacking tier — the sidebar's `z-index` exists only inside the narrow media query — but that an open overlay covers every other opener and `trapDialogKeys` swallows keydown in the capture phase, which is why `?` does nothing behind one.
- Alignment anchors for eyeballing viewer geometry changes: AO R2 P1 C03 — the LCDStatusBoard box sits on the LED digit panel of the Employees sign; AE MI P1 C24 — the HandStone box sits on the QuikSave stone. If object markers drift toward screen centers, a world-to-art transform regressed.

## Format gotchas (hard-won)

- AO camera cells are 1024×480 world units but the visible screen is a 368×240 window at +256/+120 inside the cell (1:1 unit:pixel; camera centers at `cell*1024+440`, `cell*480+240`). AE cells are 375×260, fully visible, scaled into 368×240 art. The viewer gets all of this from the `geometry` object in each data file — never hardcode per-game numbers in drawing code.
- PS1 cam images are 12 MDEC strips: `u16` length prefix + BS v3 frames in AO, `u32` prefix + BS v2 in AE; `cam2rgba` auto-detects the framing. Decoded strips assemble to 384×240 but only 368 columns are real (macroblock padding, cropped at build time).
- FG1 foreground blocks: AO partial chunks carry their own RGB555 pixels and whole sub-streams can be LZ-compressed; AE partial chunks are per-row `u32` bitmasks selecting camera-bitmap pixels and are never compressed.
- TLV records: 0x18-byte header with payload at +0x18 in AO; 0x10-byte header with payload at +0x10 in AE. Door numbers are only unique **per camera** — a target door must be resolved inside the destination camera or same-screen door pairs cross-wire.
- TLV type ids are per-game (Door is 6 in AO, 5 in AE; numbers overlap with unrelated types). Match objects by `name` in shared code, never by numeric id — except wells, whose names also differ per game (AO `WellLocal`, AE `LocalWell`) and whose arrivals can be either well type: well pairs match by the `well#` field alone, camera-bounded like the engine's arrival scan.
- An express well carries two destinations, one for each state of the switch it answers to (`disabled_well_*` / `enabled_well_*`, reaching the viewer as `to_*` / `alt_*`). Either state can be a dead end, and a dead end is written two ways: naming the well's own id, so you drop back out of the well you entered, or left unpointed at the address the fields were born with. `destOf` therefore prefers the state that *lands on another object* over the one that merely differs from the current path — the old rule handed a cross-level dead end the win over the live ride every time, because a dead end always differs. A state naming the well's own camera is a ride like any other when it names another well (the Slig Barracks hub pairs 6↔1, 5↔2, 8↔4, 7↔3 within one screen); it is only a bounce-back when nothing but the well itself answers to it.
- A destination whose level field was never set reads as level 1 (AE: Necrum Mines) while its path and camera keep the values that were right for a link inside its own level, so the triple looks plausible — 61 AE links name the Mines from another level and not one of them means it (23 naming `MI P0`, 28 the opening screen). `destTrusted` ([js/model.js](js/model.js)) believes a destination only where the partner it names is there to be found, and gates the follow, the tooltip's destination lines, the arrow stubs and `computeEntryPaths` alike. A link naming no partner (`PathTransition`) has nothing to check and stays trusted wherever it points — that is what keeps AO's two main-menu links saying "not on the map", and "not on the map" belongs to them alone. The partner check is cross-level only: `resolveTarget` is camera-bounded with a path-wide fallback, so within a level an unresolved partner is that strictness rather than bad data, and dozens of sound same-level follows depend on it. A partner *is* found when nothing at all was set — level 1, path 1, camera 1, pair id 0 is a real screen holding a placeholder numbered 0 — so `targetAt` reads that whole address as the absence it is. Key it on the level id, never on the pair number alone: AO's Monsaic Lines wells ride to `D1 P1 C1` and `F1 P1 C1`, arrival well 0 and all, and are genuine. Both the entry sets (AO 17 slots, AE 14) and the cross-level follows (AO 17, AE 12 — the games' whole level graph) are pinned in `tests/unit/map-data.test.js`; the phantoms used to badge four real Mines paths as entry points and to send 26 wells to the Mines from across Exoddus. One probably-genuine link pays for the rule: `BR P10`'s `Door@500,860` names `MI P24`, and that same address read inside the Brewery lands exactly on `BR P24`'s `door# 10`, which points back at it — a real pair whose level field alone was never set. It never worked before the check either (it read "not on the map") and the `BR P24` side still follows, so the pair shows one-way. It is the only link in either game that re-reading a dead cross-level address inside its own level would recover — the two others that resolve locally land on themselves — and that partner pointing back is the discriminator which would make such a rescue safe.
- A BirdPortal's destination words are live only when its `portal_type` is travel: a worker (rescue) or shrykull portal dies where it stands and never changes the map, so its level/path/camera fields are dead data — near-universally the unedited 1/1/1 default, which would read as a link to Necrum Mines P1 C1. Both `tlv_extra_{ao,ae}` withhold `to_*` for non-travel portals; the raw words still reach `fields`.
- A TLV carries two decoded buckets. `extra` holds *derived, semantic* fields the viewer's navigation logic reads directly (`to_level`/`to_path`/`to_cam`, `door#`, `well#`, `portal`, `view*_*`, …) — hand-written per type in `tlv_extra_{ao,ae}`, since resolving level ids and pairing doors/wells isn't a raw dump. `fields` holds the *complete raw archive* (every field, s16, dev name) for gameplay types, schema-driven. The display writes both, so a key in both buckets prints its value twice — where the archive grows to cover a word `extra` hand-decodes under the same name, `extra` gives it up (AE's express wells did, for `switch_id`); a twin under a different name is a naming question, not a duplicate (AO's `trigger_id`, the wells' `well#`). A test pins that no object names one key twice. `model.js` reads only `extra`; the field display (`js/fields.js` → `extrasText`) shows `extra` always plus the `fields` a user's `fieldPrefs` admit, prettifying enums viewer-side. `fields.js` `visibleFields()` is the single indirection: "default", "show more", and the per-type picker (`js/fieldpanel.js`, writing the per-game `fieldPrefs.byType`) are just which set it returns.
- Exoddus disc 1 ships `TL.LVL` as a 68-byte boot-config stub, not a LVL archive; the builder skips it. Archive reads are guarded (EOF raises, directories must fit their file) because a garbage header otherwise spins disc reads forever at end of image.
- Both Exoddus discs list every level, but each disc carries full content only for its half — the other half are stubs with path data and no cam files. Always pick the largest copy of a level across discs (the builder does).
- AE "ender" levels are the endgame revisits of factory areas the player returns to finish (the vaults, FeeCo Depot, Slig Barracks, Bonewerkz, the Brewery) — same map geography, a distinct level id, the game's own term. Each ender id reuses its base level's archive; the table parser deduplicates so each LVL file appears once in the level list, but TLV destinations still name the ender ids — the builder's id→short map must cover every id, not just the kept ones.
- Exoddus ships 25 paths that only its attract-mode demos play — copies of a real area, unreachable however you play — and holding a `DemoSpawnPoint` TLV is the whole rule for spotting one ([js/demo.js](js/demo.js), memoized per path; AO has no such type, so the rule degrades to "no demos" there with no per-game case). The `showDemoPaths` setting hides them from the path buttons and from search (whose summary counts what it dropped). Two properties of the shipped set carry the rest, both pinned in `tests/unit/map-data.test.js`: the games arrive at none of them and no destination `destTrusted` believes leads into one — so the entry marks, the connection arrows and their off-path stubs agree by consequence and a filter of their own would be dead code (before the destination check, two Mines demo paths wore entry badges) — and no level *opens* on one, so hiding the class never empties a level. **The path in hand is always listed**: `selectPathById` reveals a hidden path for the session, which is what lets a permalink, a remembered location or a follow land instead of falling back, and is why switching the setting off leaves the path you are standing on visible. What the path is gets said on the place panel and in the curated name (`[Demo] …`, test-enforced) — written into the string, not composed onto it at display time, so `annotations.json` reads as the list of what each place is *and* which ones are copies, and no caller has to pair a name with a marker; the test is what keeps the two honest. Never by a toast — `selectPath` re-fires on every pushed hash write, so a toast would repeat for as long as the visitor stayed.

- Static site files that are not the viewer or its data: `favicon.svg` (source of truth for the icon; `favicon-96.png` and `apple-touch-icon.png` are rasterized from it), `og-image.png` (1200×630 social card, rendered by `tools/ogcard.swift` — edit the script and rerun it, don't touch the PNG directly), `site.webmanifest`, `robots.txt`, `sitemap.xml`, `CNAME` (oddworldmap.com). Regenerate the icon PNGs from the SVG if the icon changes (a CoreGraphics Swift script was used; any SVG rasterizer works).

## Conventions

- One concern per commit; split bundled diffs before committing.
- Prose files (README, docs, this file) are never manually line-wrapped — let lines run long.
- A user-facing change ships its docs in the same commit — update the relevant README.md / CLAUDE.md, and add its `changelog.json` entry. Documenting the change is part of the same concern, not a follow-up commit.
- Changelog entries are curated, not generated: draft with `tools/changelog.py`, then rewrite into a player-facing headline + detail. The feed is a date-stamped journal of the site, not a highlights reel — any user-visible change, however small, is welcome on it; what stays out is internal work players can't perceive (refactors, tooling, CI).
- No game owns unsuffixed defaults: everything game-specific carries `ao`/`ae` in its name (files, JS globals, env vars, URL hashes). Do not reintroduce unsuffixed names for AO just because it came first.
- Generated JSON is pretty-printed (`indent=1`) so history stays diffable; keep the format stable.
- Prettier owns js/css/html formatting (`.prettierrc`: printWidth 100, defaults otherwise; exemptions in `.prettierignore` — `js/config.js` keeps its hand-aligned tables, JSON and Markdown keep their own formats). The version is pinned exactly in devDependencies because output is version-dependent (like oxipng for the PNGs); bump it deliberately: upgrade, reformat the tree in a dedicated commit, and add that commit to `.git-blame-ignore-revs`. New clones opt blame in once with `git config blame.ignoreRevsFile .git-blame-ignore-revs` (GitHub reads the file automatically).
- Format only the staged files before each commit, so the commit doesn't drag in formatter drift from unrelated files:
  ```
  git diff --cached --name-only --diff-filter=ACMR | grep -E '\.(js|css|html)$' | xargs -r npx prettier --write
  ```
  then re-stage what Prettier changed. Never run whole-tree `npm run format` as part of a normal commit — whole-tree formatting belongs in its own dedicated commit (CI runs `format:check`, so drift can't accumulate).

### Code comments

- **Default to no comment**: A comment earns its place only by recording a durable *why* the code can't show: an invariant, a constraint, a non-obvious trade-off. Keep them generic enough that a routine change doesn't force a comment edit — put a per-item note *inline on the item* (`"deaf", // ignores Abe's speech`), never in a const-doc that re-describes the set's members (that rots the moment you add one). Don't name consumers or other modules ("used by X", "the picker reads this"); don't restate a constant's value or units. Comment footprint matches code footprint — a concern touched at one line gets one comment there, not a header paragraph. Before committing, reread each comment and cut any that restates the code, names something that could be renamed, or would lie after a tune/refactor — an absent comment never goes stale.
- **No inter-diff comments**: Comments must describe the code as it is now, not how it got here. Don't write "extracted from X", "moved from Y", "duplicated here", "was previously in Z". A reader who has never seen the git history should find every comment meaningful.
- **Peer items get peer prose**: When a comment or code block enumerates parallel items — payload fields, switch cases, sibling merge loops — treat them uniformly. Don't attach a justifying clause to one item ("…and seen marks (s) — without these, restored unlocks would re-badge as new") while its siblings carry none: the asymmetry falsely flags that item as special, and the odd one out is invariably the one just added — meaning the sentence is a diff justification aimed at the reviewer, not a description aimed at the reader. Same for code shape: when the sibling loops above yours are uncommented, the new one doesn't get an explainer either. The why-this-was-added story belongs in the commit message in short form. Test: would the prose look the same if every item had been written on the same day, by one author? If your addition carries a defense its peers lack, delete the defense.
