# CLAUDE.md

Guidance for AI agents working in this repo. User-facing docs (controls, rebuild instructions, format overview) live in [README.md](README.md) — read that first; this file covers what is not obvious from the code and the traps that cost hours to find.

## Source vs generated

- Source: the viewer, under `public/` (the deploy artifact — everything in it is served, nothing outside it is) — `index.html`, `css/main.css` and the ES modules under `js/` (dependency-free vanilla JS, no build step; `js/main.js` is the boot entry, `js/state.js` holds shared state + world→draw transforms, and selection announces itself via a `selection-changed` window event so modules stay one-directional) — plus `annotations.json` and `tools/build_map.py`, `tools/cam2rgba.cpp` and the vendored `PSXMDECDecoder.*` / `Types.hpp`.
- `annotations.json`: hand-curated names/notes the discs don't provide
  - A curated name deliberately overrides the in-game one but must contain it — refine, don't erase, test-enforced. A `name` is what the game itself calls the place (AO R2's zulags, from the save slots), which is what an override has to answer to.
  - A `section` is which half of a level the path belongs to — the AE ender display name, stamped on paths nothing else names — so it sits beside the curated name rather than inside it.
  - A `nickname` is what players call a place, where the map has adopted their name for it. It stands outside the override rule, the way a `section` does: it is not the curated name, so it has nothing to refine. Keep it out of `name` as well, where a curated colon already means a sub-path of a multi-path zulag — `Zulag 10: Slig High Security` would assert a division that does not exist. It renders dimmed, taking a `·` where a name takes `—`, and only reaches the button face with "Show full names" on; below that the tooltip is its only carrier.
  - A path entry is a bare name string or `{name?, note?, nickname?}`, so only the paths with something extra to say expand and any one of the three stands alone. A note- or nickname-only entry is legal for a path but not for a level, where an entry exists only to name a level the map never renders.
  - `sanitizeAnnotations` collapses the union, so callers only ever see the object; its skip guard names every key, so a new one that is not added to it is dropped silently.
  - A note is ordinary prose, capitalized and punctuated, reaching the reader through the place panel; a nickname is the opposite, a title-case label that never closes punctuated. Both shapes are test-enforced.
  - A name the map coins itself is not a nickname and belongs in `name` (`Zulag 9: Fleech Ledge`, `Brewery Terminal`).
  - Adopting a nickname needs an entry in `tests/unit/annotations.test.js`'s `CLAIMS` table, which is keyed to exactly the nicknamed paths: a predicate over the shipped data for the fit the name claims (zulag 3 holds more drills than any other area), or the reason written down where the evidence is artwork nothing can count.
- `glossary_fields.json`: **hand-curated** (like `annotations.json`, not generated) plain-English field meanings, one game-agnostic file.
  - Three resolution tiers, most-specific first: `byType` (`"ObjectType.field"`), `byGameType` (a field's decomp game type, e.g. `Path_Slig::StartState` — the group of object types sharing that field's meaning, the same key `enum_labels` uses), `byField` (a global by name).
  - Loaded at boot (`setGlossary` in [js/glossary.js](public/js/glossary.js)); [js/fields.js](public/js/fields.js)'s `fieldHelp(game, type, field)` composes the prose with the field's full value list (from `TRANSFORM`/`enum_labels`) for the picker and screen-list definitions, handed over as a `data-tip` attribute on the field name ([js/anchortip.js](public/js/anchortip.js)).
  - Every shipped field resolves a def, pinned by test — a rebuild that surfaces a new field fails the suite until the glossary covers it — and every key is cross-checked against the shipped data so a typo can't ship. A field the engine never reads says so plainly; the graceful no-def path stays for a missing or garbage file.
  - Adding a definition is one JSON line in the tier that fits; defs are style-checked like the notes and never enumerate values — `fieldHelp` appends the value list itself.
- `glossary_types.json`: **hand-curated** (like `annotations.json` and `glossary_fields.json`) — the type encyclopedia, one plain-English paragraph per object type name under a `types` section, game-agnostic; where the two games' copies behave differently, the prose says so in words.
  - The first sentence is the summary and stands alone: the hover tooltip carries it under the object's name ([js/typeinfo.js](public/js/typeinfo.js)'s `typeSummary`), while the card shows the whole paragraph. Write entries summary-first, and keep engine claims to what the decomp confirms — the curation bar is the nicknames': describe what the shipped data and the games show.
  - A count or placement stated in prose follows the map's own counting rule — listed paths, demo copies excluded — so an entry never disagrees with the census line on its own card, and each such claim is pinned in `tests/unit/typeinfo.test.js`'s `CLAIMS` table at the scope the prose uses (a universal over the raw data pins at that scope instead).
  - The card ([js/typecard.js](public/js/typecard.js), a `.overlay` dialog) composes the paragraph with live `census()` placement counts (never hand-written — the demo footnote says what the count leaves out) and the type's glossary field defs; any surface opens it by dispatching the `typecard-open` window event, so none imports the module.
  - Style and coverage are test-enforced (`tests/unit/typeinfo.test.js`): entries read as prose, the first sentence fits a tooltip line, and the keys are exactly the shipped type set — a rebuild that surfaces a new type fails the suite until the encyclopedia covers it.
- Generated **and committed** (they are the site's data, under `public/` like the rest of it): `map_data_ao.json`, `map_data_ae.json`, `cams/ao/**`, `cams/ae/**`. Regenerate with the builder from disc images; never hand-edit.
- `field_types_{ao,ae}.json`: generated **and committed** viewer sidecar mapping each object type to its enum-typed fields' game types (`{"Slig": {"start_state": "Path_Slig::StartState", …}}`).
  - Derived from the decomp alone (no disc) via `build_map.py --emit-field-data`, and re-emitted on every normal build so it stays in sync.
  - The viewer loads it at boot (`setFieldTypes` in [js/fields.js](public/js/fields.js)) and keys value transforms by a field's game type — a value's text written once per type and shared across every object that carries it (Slig/SligSpawner/SligGetPants all share `Path_Slig::StartState`) while an unrelated same-named field stays separate (a Door's `start_state` is `DoorStates`, its own key).
  - Only enum/Choice/Scale fields appear; bare-int fields carry no type.
  - A small `_FIELD_TYPE_OVERRIDES` table applies at emission, giving a field the type it behaves as where the decomp declares one that contradicts its meaning, or supplying one the member parser can't reach at all (a data struct outside the Tlvs include graph). The schema cache stays faithful to the source either way, and why each entry exists is on the entry. An entry naming a field the schema no longer carries fails the build, and an override type is counted as used when labels are emitted, so it can never ship unlabelled.
  - Correct such quirks here in the builder, never by patching the local `alive_reversing` checkout — a patch would make the emit unreproducible from a clean tree; fixing it upstream and re-pinning is the path to retiring an override.
- `enum_labels_{ao,ae}.json`: generated **and committed** viewer sidecar mapping each enum game type to its `{value: text}` labels (`{"DoorStates": {"0": "open", "1": "closed", …}}`), so enum fields render as words without the viewer hand-maintaining them.
  - Generated by `parse_enum_labels` (`--emit-field-data`, no disc) from the decomp's enum definitions (authoritative values, explicit `= N` or positional) and its `AddEnum` blocks (curated labels, else a label derived from the enumerator name); labels are lowercased to the viewer's style, keyed to line up with `field_types`, and limited to the types some field is actually declared as (the decomp defines many enums that aren't fields).
  - Per game — the same type's values can differ (Slig `start_state` 5 is `falling to chase` in AO, `unused` in AE).
  - The basic value-types (`Choice`/`Scale`) are **excluded**: the viewer owns those semantic transforms (bool, full/half) in `js/fields.js`'s `TRANSFORM`, and a hand transform there wins over a generated label; direction enums are generated like any other (left/right).
  - Definitions are swept from the game's whole AliveLib tree plus AliveLibCommon (the include graph can't reach them all — `SwitchOp` is only ever forward-declared where fields use it), with the sibling game's tree as a fill-only fallback for shared types (AO fields use AE's `XDirection_short`).
  - Comments are stripped before parsing — the word "enum" inside one otherwise swallows the definition that follows it, and a comma inside one once minted a phantom enumerator.
  - A bare enum name defined differently in two headers, or an initializer the parser can't value, makes the type unlabelable, and the emit fails loudly if any field actually uses such a type — labels must never ship silently wrong.
- `tools/data/pathdata_ao.json` / `pathdata_ae.json`: cached level/path tables and TLV type enums parsed from the alive_reversing decompilation, used as-is by builds and only re-parsed when the cache file is deleted — which needs an `alive_reversing` checkout as a sibling directory of this repo.
  - The decomp tabulates nothing for AO's `S1`, so `discover_path_meta` reads that grid off the path chunk instead: the camera-name table heads the chunk at one 8-byte slot per cell, and the objects behind it choose among the factorisations of that count, since every object has to land inside the grid. Both halves are checked against the levels that *do* have tables — the slot run is each one's `coll_off` exactly, and the factorisation never contradicts a known grid — and it resolves `S1` to 4x10 uniquely.
  - It runs only where the table is empty, so a tabulated level is never guessed at, and it raises rather than guessing when the objects leave more than one factorisation standing. Deriving it at build time rather than hand-writing the numbers into a table is what keeps a plain rebuild reproducing the committed data.
  - A path carrying collision would break the assumption that objects start where the name table ends; `S1` has none, and one that did would fail the grid check rather than decode wrongly.
- `tools/data/objects_ao.json` / `objects_ae.json`: cached per-type field layout (`[payload word, snake_case name]` per field, plus a third element — the field's game type — where the decomp declares an enum/Choice/Scale rather than a bare int), parsed from the relive_api CTOR blocks (`Source/Tools/relive_api/Tlvs{AO,AE}.hpp`) by `parse_object_schema`.
  - Same cache discipline as pathdata (re-parsed only when deleted).
  - Drives the generic `object_fields` extractor, which emits every field of a gameplay object (`GAMEPLAY_FIELD_TYPES` in `build_map.py`) raw into `t.fields` — it reads only word+name, so the type is metadata and `map_data` is byte-identical whether or not types are present.
  - Values are read as s16 and stored raw — which fields to show and how their values render are the viewer's job ([js/fields.js](public/js/fields.js), driven by the `field_types` + `enum_labels` sidecars), so the disc is never needed again to surface or relabel a field.
  - Parser gotcha: the payload word comes from the `field_XX` hex offset in the member name, but the name lies two ways.
  - The decomp sometimes numbers *sequential* members with one offset (Door's 8 hub ids are all `field_22_hubN`); and a member of an intermediate base struct numbers from that struct's own start, so it computes *below* the payload base (`Path_WellBase`'s `field_0_scale`..`field_6_anim_id`, and ContinueZone's sole `field_10_zone_number` — Path_TLV is 0x18 wide, so the name's 0x10 lands in the rect). Both fail to increase the offset, so the one positional rule — take the next word — answers both; a below-base name must not be skipped, or the fields vanish silently with no `raw=` to show for it.
  - `_SCHEMA_LAYOUT_OVERRIDES` is left for what the CTOR genuinely can't express: an empty layout marking a field-less type (AO RingCancel) so it still retires its raw fallback. Because `object_fields` returns a dict for any schema'd type, empty included, a `GAMEPLAY_FIELD_TYPES` object never falls back to a `raw=` dump. An entry naming a type the game doesn't have, or one the parser now derives on its own, fails the build — which is why `game_setup` resolves the schema after `tlv_names`.
  - `_SCHEMA_LAYOUT_CORRECTIONS` is its sibling for a layout the CTOR expresses *wrongly* rather than not at all: the entry replaces the derived layout with the engine's own reading of the payload, and why any one of them exists is stated on the entry. Each is keyed as `(derived, corrected)`, pinned to what the parser yields today, so an upstream fix spends the entry and fails the build loudly instead of double-correcting. A correction reaches the `field_types` sidecar on any `--emit-field-data` run but the names in `map_data` only at a disc rebuild, so the two can disagree until one runs.
  - The field type comes from `parse_member_types`, which parses the data-struct member declarations across `Tlvs{AO,AE}.hpp` and every `AliveLib*` header it includes. Enum leaf names repeat across the decomp (`StartState` is both a Slig enum and a MeatSaw enum), so a nested enum is qualified with its owning struct (`Path_Slig::StartState`).
  - It reads a struct's own body only, so a base struct's members reach the *layout* but not their *type* — the wells' `scale` arrives untyped and renders raw.
- Static site files that are not the viewer or its data (all in `public/`): `favicon.svg` (source of truth for the icon; `favicon-96.png` and `apple-touch-icon.png` are rasterized from it), `og-image.png` (1200×630 social card, rendered by `tools/ogcard.swift` — edit the script and rerun it, don't touch the PNG directly), `site.webmanifest`, `robots.txt`, `sitemap.xml`, `CNAME` (oddworldmap.com).
  - Regenerate the icon PNGs from the SVG if the icon changes (a CoreGraphics Swift script was used; any SVG rasterizer works).
- `backlog/`: **hand-curated** (like `annotations.json` and `glossary_fields.json` — nothing generates it), holding plans, review findings and their outcomes in stable `item-NNN-slug.md` files.
  - Read [backlog/README.md](backlog/README.md) before filing or changing one: an existing id and path never change, its status and index bullet move together, and that README owns the body, provenance and reference rules rather than duplicating them here.

## Build & verify

- `npm run lint` — ESLint over the viewer modules, `public/sw.js` and `tests/`, each with its own globals; `tools/` is ignored. CI runs it on every push. There is no JS build step: the modules are served as-is, so lint is the only pre-runtime error check.
- `python3 -m compileall -q tools/` and `pipx run ruff==0.16.0 check tools/` — the builder's static checks; CI runs both on 3.12.
  - The ruff version is pinned exactly, like Prettier's, because which rules fire moves between releases; run it locally the same way or a clean tree can still fail CI.
  - `ruff.toml` selects the defect rules alone (undefined names, unused imports, f-string and syntax errors), not ruff's default set, which fights the parsers' deliberate compactness.
  - The supported floor is 3.8, which CI cannot exercise (EOL, absent from current runner images), so 3.9+ syntax would only surface locally.
- `python3 -m unittest discover -s tools/tests` — stdlib-only tests for the builder's pure functions (chunk walking, the LZ variant, `object_fields`' payload clamp, the label/comment/brace helpers), plus reproducibility tests that re-emit the committed `field_types_*`/`enum_labels_*` sidecars into a temp dir and compare bytes.
  - No disc image is needed; the enum-label pair skips without an `alive_reversing` checkout, so CI covers everything except those two.
  - A parser reached only through a nested helper (AE's `positional_rows`, the enum body loop) can't be tested until it's hoisted.
- `npm test` — `node --test` unit tests under `tests/unit/` for the DOM-free modules (`annotations`, `config`, `demo`, `fields`, `state`, `util`, `model`, `settings`, `searchquery`, `placesearch`, `glossary` — `imports.test.js` holds the list): geometry transforms, TLV destinations, entry paths, permalink format, settings sanitizing, plus schema checks over the shipped data files.
  - Those modules must stay importable in bare Node — no `window`/`document` at module top level (imports.test.js enforces this; `settings` additionally keeps its localStorage access inside guarded calls).
- `python3 tools/build_map.py --game AO|AE --disc <image.bin ...>` — AE takes both discs; env fallbacks are `$ODDWORLD_DISC_AO` / `$ODDWORLD_DISC_AE` (2352-byte-sector raw images).
  - `cam2rgba` is compiled automatically on first run; `oxipng` must be installed (every emitted PNG is losslessly recompressed with `-o 2 --strip safe`, so byte-determinism of images also depends on the oxipng version — committed images were made with oxipng 10.x).
- The pipeline is byte-deterministic. To verify builder changes, build into a scratch dir with `--out` and `cmp` the data file (and spot-check PNGs) against the committed outputs.
- `--levels X,Y` subset builds merge into the existing data file — they do not clobber other levels.
- Existing cam PNGs are skipped for speed, so a level whose decode previously half-completed keeps stale outputs; delete `public/cams/<game>/<LEVEL>/` for a clean rebuild of that level.
- Alignment anchors for eyeballing viewer geometry changes: AO R2 P1 C03 — the LCDStatusBoard box sits on the LED digit panel of the Employees sign; AE MI P1 C24 — the HandStone box sits on the QuikSave stone. If object markers drift toward screen centers, a world-to-art transform regressed.
  - Both of those sit at moderate depth, where a scale error is small enough to still look aligned; a scale anchor has to be near a screen's far edge. Use AE SV P7 C09 with collision lines on, where the floor line lies along the walkway deck at 200 units down, and AE MI P1 C04, where the wide LCD box covers the black panel and the LCDStatusBoard covers the small square under it.

## Viewer surfaces

- `sw.js` (in `public/` beside `index.html`, so it is served at the site root; a classic script — not an ES module; linted with `serviceworker` globals, no unit tests by design) holds two caches with two disciplines: `cams/**/*.png` cache-first in the Cache API, because GitHub Pages re-stamps HTTP validators on every deploy, and the app shell (page, code, top-level JSONs, icons) network-first in a fixed `shell-v1` bucket that serves only when the network fails — online loads stay as fresh as with no worker, and the map still opens offline.
  - It is opt-in: the worker can't read settings, so `settings.js` gates it on the `cacheMap` setting (off by default) — enable registers the worker and creates the `cams-on` marker bucket the worker checks before storing; disable deletes every `cams-*` and `shell-*` bucket and unregisters. The marker, not unregistration, is what stops caching immediately, since an already-controlling worker keeps handling fetches until reload and module state wouldn't survive an idle-worker restart.
  - Its `CACHE_NAME` is written by the builder: a content hash of `public/cams`, so regenerating a PNG expires the cache and a build that decodes nothing leaves it alone. Both games are hashed however few levels were built, since one worker serves both; a scratch `--out` holds no worker and stamps nothing. Commit the rewritten line with the artwork.
  - The shell bucket carries no such stamp: network-first entries self-refresh on every successful load, so the name only moves to retire an incompatible storage scheme. An app-page navigation stores and matches under the one key `index.html`, which is what lets `/`, `/index.html` and `/?embed=1` all boot offline — a navigation anywhere else on the origin is not the worker's to answer, so the SEO statics (og-image, robots, sitemap) can neither displace the page nor enter the cache. A redirected response is never stored: a navigation answered from one would throw rather than render.
  - The worker only caches what passes through it, so a user enable always warms — `warmShell` re-fetches everything the page already pulled (from its own performance entries, the document included) once the worker takes the page, and offline works from the enabling visit onward; a re-enable follows a sweep, so it must warm whatever still controls the page. The boot call never warms: a controlled page's own boot fetches are already the refresh.
  - After rebuilding cams locally, use DevTools → Application → "Bypass for network" (or Clear site data) to see the new images.
- `initSettings`'s `bind` is the funnel for the boolean settings: seeding the checkbox, persisting, marking a row whose value isn't its default, and the apply callback all hang off one call, so a new boolean setting gets the lot by being bound.
  - The show-more checkbox flips `fieldPrefs.mode` rather than a boolean, so it is wired by hand and is the one control that has to be updated alongside `bind`.
- Display against Settings is a taxonomy, not a layout choice. Display is what is drawn on the map right now — overlays and modes flipped mid-reading, carrying the keyboard keys, the reset button and the "Remember display & object filters" snapshot — while Settings is how the app behaves across visits (persistence, naming, field presentation). A lens that changes marker semantics (pens turn barriers from meta boxes into posts, and the ruler snaps to the post line) is still Display: from the user's seat every reading aid is the same "show me this" flip, and the semantics distinction is implementation trivia.
- `#cv`'s `touch-action` is conditional on purpose: `none` normally, `pinch-zoom` while `body.page-zoomed` is set (`js/interaction.js` watches `visualViewport.scale`, and skips both its own pinch and a touch pointer's `setPointerCapture` in that state — capture would keep the gesture from reaching the browser, while a mouse keeps its capture or a drag released off the canvas never ends).
  - `body`'s `touch-action: manipulation` is the other half: it drops double-tap zoom, and with it the tap delay a zoomable page otherwise costs, while leaving pinch alone.
- The collapsed drawer is `inert` (`syncMenu` sets it beside the menu-button state), so the controls it slides off-screen leave the tab order with it. Focus cannot enter an inert subtree at all: closing the drawer out from under the focused element moves focus to the menu button, and `/` has to open the drawer before focusing search rather than after.
- `#placePanel` ([js/place.js](public/js/place.js)) is a live region, so it announces only what is written into it while it is visible — every fill follows the unhide, and a re-selection of the path it already describes skips the write, because the pushed hash rewrite re-fires `selection-changed` on the same path constantly.
  - Chip and panel are hidden outright under an open drawer on narrow, since the drawer names the place in its own buttons — which means an open panel can be covered rather than closed, and picking a path from that drawer (the only way to pick one there) would otherwise write into a region nobody can read, so `syncPlace` holds the fill until the drawer lifts.
  - Check chip geometry on the longest label either game has, AE BA P4 (`[Demo] Block 3 Slig Bunks: Crawling Sligs`) at 390px and narrower: a representative path is short enough to hide a width regression, and the chip sits above the corner buttons in paint order, so an overlap makes them unclickable rather than merely untidy.
- [js/placesearch.js](public/js/placesearch.js) indexes the map's own places — a level, one path inside it, or one screen of a path — for the search box's Places group; it is not [js/place.js](public/js/place.js), which is the where-am-I chip.
  - A candidate carries two indexes because one blob cannot serve both halves: the *names* (level name, curated or in-game path name, nickname, section) are matched by substring the way an object's fields are, while the `LV Pn` code is held as whole tokens (`["r2", "p1"]`) and answers a term only in full. Blobbed together, the `2` in `zulag 2` is answered by the `R2` every Rupture Farms Return path sits in, and the four the game does call Zulag 2 arrive buried in all eighteen.
  - A screen candidate (`R2 P1 C3`) carries its path's blob plus the tokens naming its camera (`c3`, `c03`, the full cam name), but is listed only when a query term matches one of those camera tokens — its blob is its path's, so a bare name query would otherwise drag every matching path's whole screen list in. Clicking one centers that camera.
  - A path indexes its level's name, so a level name finds what is inside it — but `rankPlace` leaves that name out, which is what puts `Monsaic Lines` above the five paths it just pulled in.
  - The group is counted and capped apart from the objects, taking neither `HIT_CAP` nor a `GROUP_MAX` slot from them, and the summary's hit count stays an object count — which is why it has to say "no object hits" when places are the only thing on screen. Its demo-hidden tally is the one number that counts both, since a place the setting keeps off the map goes missing the way an object does.
  - Scope applies as it does to objects, except that `path` scope drops the group: the only place in scope is the one you are standing on.
- `#numbersPanel` ([js/numbers.js](public/js/numbers.js), counting in [js/census.js](public/js/census.js)) counts picked object types at four tiers at once; the screen tier is the cell under the *view center*, so it listens for `view-changed` — dispatched from `scheduleHash`'s debounced timer, the one funnel every pan, zoom and selection settles through — rather than for any pointer event.
  - A screen's objects bucket by draw-space center (the screen list's inventory rule), so the two surfaces agree on what a screen holds; counts ignore the category display filters the way search does, and follow the demo setting, tallying what hidden paths hold as a footnote.
  - The screen list keeps bottom-left and this panel bottom-right, so a desktop holds both; on narrow both become bottom sheets, so a `float-opened` event lets whichever opens close the other — narrow only, by design.
- A route ([js/route.js](public/js/route.js)) is a list of per-path segments `{lv, pa, pts}`; an armed follow seams two segments (`routeSeam` before the navigation, `routeArrive` anchoring the far side on the partner), and a same-path door pair seams exactly like a cross-path one — the polyline break is the point.
  - The one survival rule: the route lives while the selection stands on **any of its segments' paths** — so the recipient of a shared link can walk it by button, door or the back button, and only a selection the route never visits clears it. The armed follow appends its destination segment before navigating, which is how a seam into fresh territory passes; that only holds because targeted navigation (`navigateToDest`, the jump helpers) switches levels through `setLevel`, which elects no default path — `selectLevel`'s first-path selection in between would fire the rule against a path nobody chose.
  - The token is `route=nCOUNT;sLV.PA;x,y;…;end`: the count first so it outlives a cut, a marker opening every segment so no waypoint can rebind to artwork it wasn't plotted on, `end` proving the payload complete.
  - `scheduleHash`'s push-ness is sticky until the write fires (a follow's history entry must survive the silent writes riding its heels), and the seam calls `flushHash()` first, so the entry left behind holds the route as plotted — both were found by watching the back button lose the follow.
- `#minimap` paints inside [js/render.js](public/js/render.js) at the end of `draw()` — a second, tiny projection of the same frame, so it can never lag the view — while [js/minimap.js](public/js/minimap.js) holds only the scrubbing, through the same exported `minimapScale` factor the painter uses. It hides itself when the whole path fits the window, yields the bottom-right corner to the numbers panel via CSS (`:has`), is off on narrow, and deliberately not `.chrome`: an embed is exactly where orientation help is scarce.
- Barrier markers (the `BARRIERS` table in [js/config.js](public/js/config.js)) render as posts on the boundary the engine enforces — each stamp's top-left x, the same edge a hovered pen band ends on, so posts and band always meet — gated by the "Enemy patrol pens" Display toggle (`PENS.on`, off by default) together with the Enemies category; pens off, they stay ordinary meta boxes. `markerShown` is the one marker-visibility rule (drawing, hover and the ruler's snapping all ask it), so what is drawn is exactly what can be pointed at, and a post snaps on its line rather than its stamp's middle.
  - `patrolZone` ([js/model.js](public/js/model.js)) shades a hovered Slig's pen. The engine pairs bounds to sligs by id — the bound-side key is `slig_id` in AO but `slig_bound_persist_id` in AE — over a camera window that differs per game (AO ±2, AE ±3, Slig.cpp's bound loops), and the viewer honours only a unique pair; the engine's last-match-wins on duplicates is not worth imitating. Scrab bounds ship no ids, so scrabs get posts and no pen.
- The switch wiring overlay (`computeWiring` in [js/model.js](public/js/model.js), reading the per-game `WIRES` table in [js/config.js](public/js/config.js)) draws producer→consumer edges between objects whose wire fields share a live switch id — the "Switch wiring" Display toggle, off by default.
  - The engine keeps one switch-state array per level, reset only on level change (and at game start), so ids are level-scoped: same-path pairs draw as wires, and a cross-path partner reaches the hover tooltip as text ("set in P2") via `levelWiring`, which leaves demo paths out so a note never points somewhere nothing travels.
  - Ids 0 and 1 never wire: the engine hardwires them (never / always on) and producers refuse them, so a consumer's `switch_id = 1` means "always on", not a wire to something numbered 1.
  - The table is curated against the engine's actual read/write sites, and many fields named `switch_id` are not wire ends: Teleporter's `teleporter_switch_id`/`other_teleporter_switch_id` are the `tp#` pair numbers, a placed Slig's or FlyingSlig's spawner id is read only off spawner TLVs (AE's SligSpawner ships its own copy as `id`), and a drill or saw that writes its own id back at cycle end is group timing rather than wiring, so Drill/MeatSaw stay consumers — the cost is that a self-driven pair with no external producer (one exists in the shipped data) shows no wire. The near-miss to remember: HandStone's `trigger_switch_id` *is* a real write (the same Abe.cpp line MovieHandStone uses) even though the stone also copies it into a field marked unused.
  - The tooltip's wiring lines describe the drawn wires — a local partner in a hidden category is neither drawn nor named, while a cross-path note names a path rather than a marker — and state only what exists, never absence: the table is curated from the engine's verified read/write sites, so an id can always drive something it has no evidence for.
  - Hub doors (`DOOR_GATE`: AO `start_state` 2, AE `door_type` 2/3 — Door.cpp's hub/tasks-door update) AND their eight `hub_N_id`s into their own `switch_id`: the hubs are the gate door's inputs and its own id its output alone, since the gate rewrites that id every frame and an external feed could never hold it.
  - An edge hides with either endpoint (`markerShown` both ends), and a wire to a barrier post lands on the post's line, as the ruler's snap does.
  - `tests/unit/wiring.test.js` pins the per-game edge totals and cross-checks every table key against the shipped data, so a typo'd key cannot ship silently.
- `#anchorTip` ([js/anchortip.js](public/js/anchortip.js)) explains any element carrying a `data-tip` attribute. The attribute is the entire interface — there is no registration call and none is wanted; a class like `.gloss` is only the visual cue, so a new consumer writes an attribute and no JS.
  - Because an attribute carries a string and nothing else, the line break is the content model: the first line is the summary, the rest a dimmer `.detail` block.
  - It is a `<body>` child and `position: fixed` because the surfaces that host one scroll (`#sidebar`, `#camPanelBody`) and would clip a tooltip parented inside them; that is the whole difference from `#tip`, which is absolute inside `#main` and clamps against the canvas. `pointer-events: none` is what stops it costing a click on the chrome it crosses.
  - Nothing here calls `preventDefault`: the tap must still reach whatever the anchor sits inside, so one tap both explains a field and ticks it.
  - `pointerover`/`pointerout` are filtered to `pointerType === "mouse"`: a touch fires both around its own tap, so an unfiltered pair would show the tooltip and hide it again inside one gesture.
  - Leaving is asked of the anchor (`anchor.contains(relatedTarget)`) rather than re-resolved from the attribute, so an anchor with element children doesn't flicker as the pointer crosses between them.
  - Check the placement against the bottom edge, where it flips above the anchor, and at 320px, where the width clamp engages.
- `#about` ([js/about.js](public/js/about.js)) is the fourth dialog on the `.overlay`/`.dialog` + `trapDialogKeys` pattern, and the first to hold links, which is why the trap's tab set counts `a[href]` — the other three hold only controls, so widening it changed nothing for them.
  - Its prose is static markup rather than built by the module, so the notice is in the page source with scripting off, and it is deliberately not `.chrome`, so it survives an embed.
  - It states no licence, and that is a decision rather than an omission: the repo holds code written here, one vendored file under another author's copyright, and artwork this project cannot license at all, so a single line of terms in the app would claim all three.
  - What keeps two dialogs from ever being open together is not a stacking tier — the sidebar's `z-index` exists only inside the narrow media query — but that an open overlay covers every other opener and `trapDialogKeys` swallows keydown in the capture phase, which is why `?` does nothing behind one.
- `#whatsnewFilter` ([js/whatsnew.js](public/js/whatsnew.js)) builds the What's New tag row from the tags `changelog.json` actually carries rather than from a list in the code, so a new tag needs no JavaScript.
  - Give it a colour rule or it takes the dim default, and add one word to `tests/unit/changelog.test.js`'s tag set, which is the only thing standing between a typo'd tag and a phantom chip nothing catches.
  - The chip's *fill* is what says on or off, because the text colour belongs to the tag. Do not reach for opacity: `fixed` is already dim, so fading it says nothing.
  - `flagship` is an entry's second axis rather than a fourth kind: a `"flagship": true` beside the kind it keeps, a chip appended after the sorted kinds so it lands where a sorted fourth tag could not, and a badge beside that kind on the entry (`labelsOf`, the one place in the module that names it).
  - A flagship answers to **its own chip alone**, which is what lets the three kinds switch off and leave the flagships by themselves. It cannot also answer to its kind's chip: every flagship is new, so an entry surviving on either label would leave the flagship chip inert, and one needing both would make the kinds' chips hide what the flagship chip is there to isolate.
  - One `--foil` token, because the badge, its chip and the entry's rail have to agree on it. The chip takes it as a *fill* where the badge takes it as clipped text: `background-clip: text` would clip the chip's own fill away, and the fill is the on/off signal. Naming the on state (`[aria-pressed="true"]`) outranks the off rule from anywhere in the sheet, so off needs no flagship case at all. In the reduced-motion block the foil stays and only the sweep and the sheen go — the gradient is colour, the travel is motion.

## Format gotchas (hard-won)

- Both games address cameras on a grid coarser than the screen, and in both the visible screen is a **368×240 window of world units** inside the cell, world units being PS1 screen pixels and the artwork 1:1 with them. AO's cell is 1024×480 with the window at +256/+120 (camera centers at `cell*1024+440`, `cell*480+240`); AE's is 375×260 with the window at +0/+0. The viewer gets all of this from the `geometry` object in each data file, so never hardcode per-game numbers in drawing code.
  - The authorities are `Map::Get_Camera_World_Rect_481410` (AE, which states the 368×240 box outright) and AO's `Rect_Location_Relative_To_Active_Camera_4448C0`, whose ±184/±120 test around the camera center is the same box. **Do not read AO's own `Get_Camera_World_Rect_444C30` as the window**: it returns a 640-wide box, which is the PC screen width leaking into PSX-space coordinates.
  - Everything outside the window is addressing slack the game never renders and the player never occupies: a camera change teleports the character across it, preserving the within-cell offset (`VOnPathTransition_401470` in AO, `vOnPathTransition_408320` in AE). Level authors still parked objects and ran collision lines through it, so the packed layout draws those over a neighbouring screen.
  - `cellW`/`cellH` are the pitch screens are drawn at, not a scale: a screen's interior is always 1:1, and the pitch being narrower than the cell is what folds the slack away. Giving `visW`/`visH` the whole cell rather than the window is what turns that pitch into a squash, dragging every object and collision line toward its screen's top-left corner by an error that grows with the distance from it.
- PS1 cam images are 12 MDEC strips: `u16` length prefix + BS v3 frames in AO, `u32` prefix + BS v2 in AE; `cam2rgba` auto-detects the framing. Decoded strips assemble to 384×240 but only 368 columns are real (macroblock padding, cropped at build time).
- FG1 foreground blocks: AO partial chunks carry their own RGB555 pixels and whole sub-streams can be LZ-compressed; AE partial chunks are per-row `u32` bitmasks selecting camera-bitmap pixels and are never compressed.
- TLV records: 0x18-byte header with payload at +0x18 in AO; 0x10-byte header with payload at +0x10 in AE. Door numbers are only unique **per camera** — a target door must be resolved inside the destination camera or same-screen door pairs cross-wire.
- TLV type ids are per-game (Door is 6 in AO, 5 in AE; numbers overlap with unrelated types). Match objects by `name` in shared code, never by numeric id — except wells, whose names also differ per game (AO `WellLocal`, AE `LocalWell`) and whose arrivals can be either well type: well pairs match by the `well#` field alone, camera-bounded like the engine's arrival scan.
- An express well carries two destinations, one for each state of the switch it answers to (`disabled_well_*` / `enabled_well_*`, reaching the viewer as `to_*` / `alt_*`).
  - Either state can be a dead end, and a dead end is written two ways: naming the well's own id, so you drop back out of the well you entered, or left unpointed at the address the fields were born with.
  - `destOf` therefore prefers the state that *lands on another object* over the one that merely differs from the current path, since a dead end always differs. A state naming the well's own camera is a ride like any other when another well answers to it (the Slig Barracks hub pairs 6↔1, 5↔2, 8↔4, 7↔3 within one screen), and a bounce-back only when nothing but the well itself does.
- A destination whose level field was never set reads as level 1 (AE: Necrum Mines) while its path and camera keep the values that were right for a link inside its own level, so the triple looks plausible — 61 AE links name the Mines from another level and not one of them means it (23 naming `MI P0`, 28 the opening screen).
  - `destTrusted` ([js/model.js](public/js/model.js)) believes a destination only where the partner it names is there to be found, and gates the follow, the tooltip's destination lines, the arrow stubs and `computeEntryPaths` alike.
  - A link naming no partner (`PathTransition`) has nothing to check and stays trusted wherever it points — that is what lets AO's two main-menu links follow into `S1`, whose grid the decomp does not tabulate.
  - No destination in either game now names a level the map does not render, so the off-map-level branch the tooltip carries is unreachable against the shipped data and `annotations.json`'s `levels` section is empty in both games; both are kept for data that could name one, not because anything does.
  - The partner check is cross-level only: `resolveTarget` is camera-bounded with a path-wide fallback, so within a level an unresolved partner is that strictness rather than bad data, and dozens of sound same-level follows depend on it.
  - A partner *is* found when nothing at all was set — level 1, path 1, camera 1, pair id 0 is a real screen holding a placeholder numbered 0 — so `targetAt` reads that whole address as the absence it is.
  - Key it on the level id, never on the pair number alone: AO's Monsaic Lines wells ride to `D1 P1 C1` and `F1 P1 C1`, arrival well 0 and all, and are genuine.
  - Both the entry sets (AO 17 slots, AE 14) and the cross-level follows (AO 17, AE 12 — every crossing the shipped data can follow, which is one short of the games' own: Necrum Vaults to FeeCo Terminal 1 happens in a cutscene and no well pairs for it) are pinned in `tests/unit/map-data.test.js`; the phantoms used to badge four real Mines paths as entry points and to send 26 wells to the Mines from across Exoddus.
  - One probably-genuine link pays for the rule, and shows one-way rather than not at all: `BR P10`'s `Door@500,860` names `MI P24`, an address that read inside the Brewery lands on `BR P24`'s `door# 10`, which points back at it. It is the only link in either game a local re-read would recover, it never followed before the check either, and the `BR P24` side still does — so leave it.
- A BirdPortal's destination words are live only when its `portal_type` is travel: a worker (rescue) or shrykull portal dies where it stands and never changes the map, so its level/path/camera fields are dead data — near-universally the unedited 1/1/1 default, which would read as a link to Necrum Mines P1 C1.
  - Both `tlv_extra_{ao,ae}` withhold `to_*` for non-travel portals; the raw words still reach `fields`.
- A TLV carries two decoded buckets. `extra` holds *derived, semantic* fields the viewer's navigation logic reads directly (`to_level`/`to_path`/`to_cam`, `door#`, `well#`, `portal`, `view*_*`, …) — hand-written per type in `tlv_extra_{ao,ae}`, since resolving level ids and pairing doors/wells isn't a raw dump.
  - `fields` holds the *complete raw archive* (every field, s16, dev name) for gameplay types, schema-driven.
  - The display writes both, so a key in both buckets prints its value twice — where the archive grows to cover a word `extra` hand-decodes under the same name, `extra` gives it up (AE's express wells did, for `switch_id`); a twin under a different name is a naming question, not a duplicate (AO's `trigger_id`, the wells' `well#`). A test pins that no object names one key twice.
  - `model.js` reads only `extra`; the field display (`extrasText` in [js/util.js](public/js/util.js), over `fieldEntries` from `js/fields.js`) shows `extra` always plus the `fields` a user's `fieldPrefs` admit, prettifying enums viewer-side.
  - `fields.js` `visibleFields()` is the single indirection: "default", "show more" and the per-type picker (`js/fieldpanel.js`, writing the per-game `fieldPrefs.byType`) are just which set it returns. Search is the fourth caller and the exception — it asks for `"all"` and gets that string back rather than a set, which `fieldEntries` special-cases.
- Exoddus disc 1 ships `TL.LVL` as a 68-byte boot-config stub, not a LVL archive; the builder skips it. Archive reads are guarded (EOF raises, directories must fit their file) because a garbage header otherwise spins disc reads forever at end of image.
- Both Exoddus discs list every level, but each disc carries full content only for its half — the other half are stubs with path data and no cam files. Always pick the largest copy of a level across discs (the builder does).
- AE "ender" levels are the endgame revisits of factory areas the player returns to finish (the vaults, FeeCo Depot, Slig Barracks, Bonewerkz, the Brewery) — same map geography, a distinct level id, the game's own term.
  - Each ender id reuses its base level's archive; the table parser deduplicates so each LVL file appears once in the level list, but TLV destinations still name the ender ids — the builder's id→short map must cover every id, not just the kept ones.
- Exoddus ships 25 paths that only its attract-mode demos play — copies of a real area, unreachable however you play — and holding a `DemoSpawnPoint` TLV is the whole rule for spotting one ([js/demo.js](public/js/demo.js), memoized per path; AO has no such type, so the rule degrades to "no demos" there with no per-game case).
  - The `showDemoPaths` setting hides them from the path buttons and from search (whose summary counts what it dropped).
  - Nothing arrives at one and no level opens on one, both pinned in `tests/unit/map-data.test.js`, so the entry marks and the connection arrows need no demo case of their own.
  - **The path in hand is always listed**: `selectPathById` reveals a hidden path for the session, which is what lets a permalink, a remembered location or a follow land instead of falling back, and is why switching the setting off leaves the path you are standing on visible.
  - That a path is a copy is written into its curated name (`[Demo] …`, test-enforced) rather than composed on at display time, so no caller has to pair a name with a marker.

## Conventions

- One concern per commit; split bundled diffs before committing.
- Everything committed reads as its final state, written once — code comments, docs, backlog items, commit messages and the shape of history alike. A follow-up that reshapes something still unpushed folds into the commit that introduced it, message rewritten to describe only what ships, rather than landing as an add-then-amend pair; narration of rounds, actors and supersessions belongs in no committed text. The test: would it read the same if one author had written it in one sitting?
- A fixup commit targets the commit that introduced the text it corrects and sits directly after it, so an autosquash is a pure fold — a fixup authored on top of later commits carries their lines as context and conflicts when hoisted past them. After any history rewrite, diff the old head against the new (only the intended change may appear) and dry-run the autosquash on a throwaway branch before handing the branch over.
- Prose files (README, docs, this file) are never manually line-wrapped — let lines run long.
- A user-facing change ships its docs in the same commit — update the relevant README.md / CLAUDE.md, and add its `changelog.json` entry. Documenting the change is part of the same concern, not a follow-up commit.
- Changelog entries are curated, not generated: draft with `tools/changelog.py`, then rewrite into a player-facing headline + detail. The feed is a date-stamped journal of the site, not a highlights reel — any user-visible change, however small, is welcome on it; what stays out is internal work players can't perceive (refactors, tooling, CI).
- No game owns unsuffixed defaults: everything game-specific carries `ao`/`ae` in its name (files, JS globals, env vars, URL hashes). Do not reintroduce unsuffixed names for AO just because it came first.
- Generated JSON is pretty-printed (`indent=1`) so history stays diffable; keep the format stable.
- Prettier owns js/css/html formatting (`.prettierrc`: printWidth 100, defaults otherwise; exemptions in `.prettierignore` — `public/js/config.js` keeps its hand-aligned tables, JSON and Markdown keep their own formats).
  - The version is pinned exactly in devDependencies because output is version-dependent (like oxipng for the PNGs); bump it deliberately: upgrade, reformat the tree in a dedicated commit, and add that commit to `.git-blame-ignore-revs`.
  - New clones opt blame in once with `git config blame.ignoreRevsFile .git-blame-ignore-revs` (GitHub reads the file automatically).
- Format only the staged files before each commit, so the commit doesn't drag in formatter drift from unrelated files:
  ```
  git diff --cached --name-only --diff-filter=ACMR | grep -E '\.(js|css|html)$' | xargs -r npx prettier --write
  ```
  then re-stage what Prettier changed. Never run whole-tree `npm run format` as part of a normal commit — whole-tree formatting belongs in its own dedicated commit (CI runs `format:check`, so drift can't accumulate).

### Stylesheet vocabulary

[css/main.css](public/css/main.css) has one shared vocabulary and a new surface reaches for it rather than restating a treatment. A value becomes a `:root` token when components that are otherwise unalike have to agree on it; a treatment that recurs whole becomes a class; a repetition that is only two numbers coinciding is left alone.

- **Controls inherit the page font.** Browsers hand `button`/`input`/`select`/`textarea` a font of their own, so a reset beside the `*` rule gives them the page's, and no rule below it has to name a family to undo that — the three that do name one are asking for something (`--serif` for the What's New masthead and its dates, `inherit` on `kbd` to escape the UA's monospace).
  - Reach for `font-family`, never the `font:` shorthand, which also resets size, weight and line-height — measured, that takes the level and path buttons from 12px to 13px and the close glyph's box from 18x24 to 12x19.
  - `font-family` alone still costs one pixel of height on the 11px controls (the search scope buttons and the search results' "show more" rows), where the page font's normal line-height is a pixel taller than the UA font's.
- **Colour and depth are tokens; size is not.** `--over-rgb` is the one near-black everything floating over the map is tinted from, each surface picking its own alpha over it, `--surface-float` the opaque tier of it the two tooltips, the screen list and the place panel share, and `--shadow-float` / `--shadow-modal` the two elevations.
  - Radii and paddings are deliberately left alone — a scale over 5/6/8px would buy indirection rather than agreement, since nothing breaks when two components pick different ones.
- **Stacking tiers** sit in `:root` low to high, so their order states a system nothing else in the repo did: `--z-map-overlay`, `--z-tip`, `--z-scrim`, `--z-drawer`, `--z-map-chrome` (which has to beat the drawer it opens over), `--z-anchor-tip`, `--z-modal`.
  - `--z-tip` is directly above the map overlays because a hover tooltip is the affordance the pointer is actively producing and must not be clipped by a surface that is merely present; `pointer-events: none` is what makes that safe, since nothing underneath loses a click.
  - Do not try to solve that with `#cv`'s `pointerleave`, which fires only while the *cursor* is inside an overlay: the tooltip's box sits 16px down and right of the cursor and can be 340px wide, so it reaches onto all four overlays from outside them.
  - It stays *below* `--z-map-chrome` and the corner buttons do still cover it: a flat scale cannot put the tooltip over chrome while keeping it under the drawer chrome exists to beat, and being covered by a corner button is the better of the two failures.
- **A dialog** is `.overlay` wrapping `.dialog`, holding `.dlg-head` / `.dlg-body` / `.closebtn` (which the screen list's close shares, at its own size), with the module toggling `.open` on the overlay.
  - The state is on the element rather than on `body` precisely so the stylesheet never names a dialog — a fifth costs no CSS at all unless its width differs from the fallback in `width: var(--dialog-w, 460px)`, written as a fallback rather than a declaration so the token doesn't inherit into every descendant.
  - The reduced-motion group has to name `.overlay.open` beside `.overlay`, because the open state carries a transition that one class cannot outrank.
- **`.linkbtn`** is the no-chrome underlined text button: the heading tools, the Fields picker's pair, the sidebar footer and the route bar's undo/clear.
  - It declares no font, deliberately — size is per-surface (11px in the footer, 12px in the route bar, the heading's own for a heading tool), and a `font:` shorthand on the class would break two members in opposite directions, since `.h2tools`'s pair inherits its `h2`'s bold and uppercase while the route bar's keeps the UA `line-height: normal`.
  - Hover is guarded with `:not(:disabled)`, which is what the route bar needs and no other member exercises; `:focus-visible` takes the same accent, for every member.
- **`.rowbtn` and `.listhead`** are the full-width row that behaves as a button, with its hover and `.active` states, and the small uppercase divider above a run of them; the screen list and the search results share both. Each is added alongside the component's own class (`rowbtn cp-row`, `listhead shead`), so what is shared and what is local stay legible in the markup.
- **`.checkrow`** is a checkbox and its wording on one line, across the object filters, the Display toggles, the Settings dialog and the Fields picker.
  - Selection is suppressed on the class rather than per surface — a label you click repeatedly should not select its wording anywhere — while padding stays per-surface, which is what keeps the narrow query's fatter touch targets on the two sidebar surfaces and off the dialog's rows.

### Code comments

- **Default to no comment**: A comment earns its place only by recording a durable *why* the code can't show: an invariant, a constraint, a non-obvious trade-off.
  - Keep them generic enough that a routine change doesn't force a comment edit — put a per-item note *inline on the item* (`"deaf", // ignores Abe's speech`), never in a const-doc that re-describes the set's members (that rots the moment you add one).
  - Don't name consumers or other modules ("used by X", "the picker reads this"); don't restate a constant's value or units.
  - Comment footprint matches code footprint — a concern touched at one line gets one comment there, not a header paragraph.
  - Before committing, reread each comment and cut any that restates the code, names something that could be renamed, or would lie after a tune/refactor — an absent comment never goes stale.
- **No inter-diff comments**: Comments must describe the code as it is now, not how it got here. Don't write "extracted from X", "moved from Y", "duplicated here", "was previously in Z". A reader who has never seen the git history should find every comment meaningful.
- **Peer items get peer prose**: When a comment or code block enumerates parallel items — payload fields, switch cases, sibling merge loops — treat them uniformly.
  - Don't attach a justifying clause to one item ("…and seen marks (s) — without these, restored unlocks would re-badge as new") while its siblings carry none: the asymmetry falsely flags that item as special, and the odd one out is invariably the one just added — meaning the sentence is a diff justification aimed at the reviewer, not a description aimed at the reader.
  - Same for code shape: when the sibling loops above yours are uncommented, the new one doesn't get an explainer either.
  - The why-this-was-added story belongs in the commit message in short form.
  - Test: would the prose look the same if every item had been written on the same day, by one author? If your addition carries a defense its peers lack, delete the defense.
